# Response templates

One per category. Adapt them; do not paste them verbatim.

## Insufficient repro

> Thanks for the report. To dig into this I need a couple of things:
>
> - <missing item, named specifically>
> - <missing item, named specifically>
>
> With those I can try to reproduce it.

Name the items. Never write "please provide more information".

## Possible duplicate

> Thanks for the report. This looks related to #<n>, which describes <the shared
> symptom>. Could you check whether the details there match what you are seeing?
> If it turns out to be different, tell us what differs and we will keep this
> one open.

Never assert it is the same issue. Never say the issue will be closed.

## Confirmed duplicate

> Thanks for the report. This is the same problem as #<n> — <one line on why>.
> Following that thread will get you the updates.

Still no closing, and no timeline.

## Confirmed bug, sufficient repro

> Thanks, this is a clear report. Reproduced steps and version noted; labelling
> it as <label> so it is on the list.

Do not say "we will fix this soon".

## Feature request

> Thanks for the suggestion. Recording it as a feature request. To help weigh it
> up: what are you trying to accomplish, and what are you doing today instead?

Never accept or reject on the maintainer's behalf.

## Support question

> This looks like a usage question rather than a bug. <Pointer to the relevant
> docs section, if one genuinely exists.> If the docs do not cover your case,
> say so and we will treat it as a docs gap.

Only link documentation you have actually read. Never invent a docs URL.

## Docs gap

> Good catch — the documentation is wrong here, not the code. Labelling this as
> a docs issue.
